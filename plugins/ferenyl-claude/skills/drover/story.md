# Story mode
The user works from issues/work items/stories. State: `<HID>/stories.json`, `<HID>/stories/<sid>.md` (description + clarifications; agents read it, never paste it).

```
drover.sh story <HID> fetch <ref...> [repo=o/r] [tracker=github|azure|jira] [org=URL] [query="..."] [id=<sid>]
drover.sh story <HID> add <sid> "<title>" [tracker= key= url= source= type= assignee= state= file=F]   # import after an MCP fetch
drover.sh story <HID> mode parallel|sequential [planner=y|n] [flow=<name>] [azure_config=DIR|-] [merge_all=squash|merge|-]   # pr=y|n pr_review=y|n = deprecated aliases (commit|pr|pr-review)
drover.sh story <HID> set <sid> [status=S|auto] [blocked="reason"|-] [order=N] [clarify="answer"] [branch=B] [worktree=W] [assignee=A] [pr=<url|nr>|-]
drover.sh story <HID> list | show <sid>          # also refresh open PRs, at most once per 60 s
drover.sh story <HID> assign <sid> [--yes]      # tracker assignee = current CLI user (tracker-assign, else --yes after a yes; exit 6 = not in flow)
drover.sh story <HID> comment <sid> "<text>" [--yes]   # comment on the work item (tracker-comment)
drover.sh story <HID> pr <sid> [--draft] [--title T] [--body-file F] [--link] [--yes]   # push branch, create PR (pr|pr-draft; pr-draft forces --draft); --link: push + print the create-PR link (pr-link|pr); `set <sid> pr=<url|nr>` records one an agent made via MCP
drover.sh story <HID> checks <sid>              # watch CI in the background: inbox "checks <sid>: passed|failed|none"
drover.sh story <HID> sync                      # refresh PR state/review
spawn ... --story <sid>  ·  worktree <HID> <sid>-<role> --story <sid>  ·  task add ... story=<sid> kind=plan|impl|review|pr
```
Refs: issue URL/`#N` (github), work item URL/id (azure), `KEY-12`/browse URL (jira). Exit 5 = CLI missing/unauthenticated: fetch/write via the tracker MCP, then `story add` / `story set`. Azure exit 5 first: the user may be logged in from another folder: look in the instructions in effect (CLAUDE.md) for an az config path, else ask the user whether there is an az login in another folder; then `story mode azure_config=DIR` and retry; use the MCP only if that fails. azure_config is exported as AZURE_CONFIG_DIR for the `az` calls of `story` only, not for agents' own `az` or an Azure DevOps MCP.
Statuses: backlog · planning · working · waiting-for-user · review · done; derived from tasks/agents/PR. `status=S` pins one, `status=auto` unpins. `blocked=` is a badge, not a status.

## Flow
1 `story fetch` (or MCP + `story add`), show `story list`.
2 Unclear story (what is wrong/what to do?): `story set <sid> status=waiting-for-user`, ask the user, then `story set <sid> clarify="..."` (unpins). Ask whether to post the answer on the work item → `story comment`.
3 One AskUserQuestion batch: sequential or parallel (parallel ⇒ one worktree per story) · planner? (skip if the user asked for one) · git/PR flow (SKILL.md; options `pr-approve` (Recommended) · `pr-draft` · `pr` · `pr-merge`, "Other" = numbered list of all flows as in SKILL.md, answer number or name; per-story override: `flow <HID> <name> --story <sid>`) · agents in auto mode or not (spawn `--perm auto` / `--perm acceptEdits`; switch later with `perm`)? · assign the work items to you? → `story mode ... flow=<name>`; on yes `story assign` each. Steps in the chosen flow are pre-approved: do them without asking again; ask again only on blocking findings or changed scope.
  Sequential: stories by `order`, one at a time, one branch per story (`story set <sid> branch=`).
4 Planner first (if chosen): spawn it before any other agent; tasks `kind=plan story=<sid>` (one planner for all, or `<sid>-plan` per story when parallel). Spawn it with `--perm plan`; it writes the plan file and reports done, no ExitPlanMode (see SKILL.md Workflow 1). It plans the solution and always proposes the agents (id, purpose, model, auto or not) per story into a plan file. Models: opus plans the contract (shared design, interfaces); sonnet plans each small story. The plan template requires per story: a verified test command (it was run), build prerequisites, line endings (repo convention), and the consumers of every changed DTO/interface. Show its agents to the user before spawning; every other story task `depends=` its plan task.
5 Story agents (small story: the dev writes its tests, one shared `review` agent reviews all stories' code, the full test suite runs once at the end, not per story): id `<sid>-<role>`, `spawn ... --story <sid>`; tasks `<sid>-<name>` (story is inherited from the owner). Parallel: `worktree <HID> <sid>-dev --story <sid>` as cwd.
6 "How is story X / the stories going?": `story show <sid>` / `story list`, not `read`.
7 Tracker/host writes follow the write-approval rule in SKILL.md: only steps in the flow (tracker-assign, tracker-comment, …), else ask the exact action. `story` writes only `assign` and `comment`, never statuses; other tracker writes (status, link) by an agent only if the flow lists them.
8 Branch names, commit messages and PR title/body are not hardcoded: before branching/committing/opening a PR read the instructions in effect (global + project CLAUDE.md, CONTRIBUTING, PR templates), follow them (`worktree --branch <name>`, `story pr --title/--body-file`), and ask the user if nothing is specified.
9 Review before PR: flows with `pr-link`/`pr`/`pr-draft` chain dev → review (local diff) → pr task via `depends=`. Story tasks done: PR per the flow (`manual-pr`: `story pr <sid> --link`, the user opens it) → build the body file from the PR template yourself, then `story pr <sid> --body-file F` (without it the body is empty).
10 PR review (flow has `review-post`; a separate review of the PR diff, not the step 5 reviewer): spawn `<sid>-prreview` (sonnet; opus for large diffs; `--mcp <host server>` if it must read PR comments or work-item images), task `kind=review` `depends=` the pr task; it posts comments only, no reject votes; with `review-approve` it votes approve only if it found nothing blocking (GitHub refuses approving your own PR: then report instead). With `review-fix` a fix task follows, then checks/merge tasks (`checks`, `merge-pr`), each `depends=` the previous.
11 After `story pr`: `story checks <sid>`, then wait for its inbox line (no polling). `story sync` before reporting PR state. Merge the PR only if the flow has `merge-pr` (after green checks and review), else ask. `merge-ask`: after green checks and the PR review (approve), if `story_mode.merge_all` is set, merge that way without asking; else AskUserQuestion "Complete PR <url>?" Squash (Recommended) · Merge commit · Squash all · Merge all ("Other" = not now); "… all" → `story mode merge_all=squash|merge` (applies to this and every later PR of the corral; `-` clears). Squash/merge: do it yourself (`gh pr merge <url> --squash|--merge`, `az repos pr update --id <nr> --status completed --squash true|false`, `glab mr merge <nr> [--squash]`), then `story sync`. User says a PR is merged, or the next story starts: `story sync`, check `story list` (merged ⇒ `done`), then `git fetch` and `worktree` for the next story (base = origin/HEAD). No PR: after the user accepts, `story set <sid> status=done`.
